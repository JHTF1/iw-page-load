## 一、30 秒口径

- **Q1 事实**：25 个真实站点，initcwnd 范围 2.29～5.15 MSS，中位数 3.78，均值 3.67；15/25 低于 4 MSS，没有站点达到 RFC 6928 建议的 10 MSS。
- **Q2 相关**：TTFB ~ initcwnd 的 ρ = −0.183（p = 0.382）；load ~ initcwnd 的 ρ = −0.305（p = 0.138）；控制 `transfer_bytes` 后偏相关 −0.245（p = 0.249）；n = 25，三项均不显著。
- **Q3 因果**：受控四组 load 中位数 729.55 / 599.30 / 596.65 / 467.60 ms；2→10 降 18.2%，2→20 降 35.9%，10→20 降 21.6%，4→10 仅 −0.4%；效应量全部 ±1.0，Bonferroni 校正后 p = 0.120～0.311，精确检验校正后 0.095～0.343，均不显著。
- **数据质量**：amazon/yahoo 是拦截页（1 633 B / 3 669 B）；microsoft 的 initcwnd 只有 1/2 轮；真实 HTTPS 首飞是配置窗口下界；36kr 有 2 轮 load=0（只剔除这 2 轮后 ρ = −0.304，p = 0.139；整站剔除 ρ = −0.214，p = 0.315，结论均不变）；单机单点测量。

## 二、A 的抓包算法（自己负责）

**Q1：你们到底测的是什么？**

A：测服务器在客户端第一次确认其数据之前发出的 TCP 载荷字节数。单位是 MSS，输出 `initcwnd_bytes`、`mss_bytes`、`initcwnd_mss` 和置信度。真实站点只把它当观测首飞下界，受控实验用来验证算法。

**Q2：为什么首窗口终点不是握手 ACK？**

A：HTTPS 里客户端在握手 ACK 之后才发 ClientHello，服务器收到请求才发 ServerHello、证书等首飞数据；如果把握手 ACK 当终点，会统计到 0 字节。正确终点是第一个 `ack > 服务器 ISN+1` 的客户端 ACK。

**Q3：重传、乱序怎么处理？**

A：把每个服务器载荷段映射成相对服务器 ISN 的序号区间 `[start, start+len)`，对所有区间求并集；重传只在 `retrans_count` 里计数，乱序靠区间合并，二者都不重复计字节。序号按 32 位环绕处理，落在 ISN 之前的区间丢弃。

**Q4：为什么不数报文段？**

A：网卡 GRO/LRO/TSO 会把多个 TCP 段合并成一个大段，段数会失真；所以只算字节，`segment_count` 只作参考，不参与结论。

**Q5：MSS 为什么取两端较小值？**

A：服务器的实际发送段长受客户端 MSS 和路径 MTU 共同限制。实验室客户端 SYN 报 1460，服务器 SYN-ACK 报 1392（WSL MTU 1432），服务器实际按 1392 发包；只除客户端 MSS 会把 lab-10 算成 9.53。取两端较小值后四组精确为 2/4/10/20。任一侧非正或缺失时回退到另一侧或协议默认值，并降低置信度。

**Q6：算法怎么校准？**

A：在 WSL2 nginx 平台上用单个 60 KB 对象，`tc netem` 设 60 ms 单程时延，`ip route` 把 initcwnd 设为 2/4/10/20 四组，每组 5 轮，用 curl 单连接请求。四组 20/20 成功，测得 2.0/4.0/10.0/20.0 MSS，误差 0，置信度全部 high。

**Q7：真实站点抓了多少轮？为什么是 49/50？**

A：25 个真实站点，每站 2 轮。microsoft 第 1 轮 curl 超时 8 000 ms，第 2 轮成功，所以有效 49/50。代表轮按“置信度 → 与中位数距离 → 重传数”选，失败站点只记日志、不中断整批。

**Q8：百度 3.83 MSS 怎么来的？**

A：百度实测首飞 5206 B，客户端 SYN MSS=1460、服务器 SYN-ACK MSS=1360，取较小值 1360，`5206/1360=3.83`。早期用客户端 1460 算是 3.57，11/03 校准后已修正。

**Q9：为什么真实站点值是下界？**

A：真实 HTTPS 首飞可能受 TLS 握手报文数量限制，服务器实发字节数可能小于配置窗口；抓包所得是配置窗口的下界，不能直接当作服务器的精确配置值。因果结论用受控实验的四组数据。

**Q10：抓包和测量为什么要分开？**

A：测 initcwnd 只用 curl 单连接，浏览器会并行开多条连接，首窗口互相干扰；测加载性能用 Chrome 冷缓存、禁 QUIC。两条线分开执行，最后按 `site` 合并。

**Q11：抓包用什么工具？**

A：scapy 的 AsyncSniffer，BPF 过滤 `tcp and host <服务器 IP>`；先用 `getaddrinfo` 解析域名，再用 `curl --resolve` 钉住 IP，`--noproxy "*"`、`--http1.1`、不跟随重定向。真实站点用 WinPcap 4.1.3，受控实验用 WSL tcpdump，两种后端输出相同格式 pcap，算法不依赖后端。

**Q12：多连接、抓包截断怎么办？**

A：按四元组去重取最早一条，并在置信度中降级；没有找到确认服务器数据的 ACK 时统计到抓包结束、置信度降为 medium；没有完整握手或首窗口无载荷则拒绝产出数据。

## 三、B 的平台与数据质量（A 代表小组回答）

**Q13：为什么用 WSL2 + nginx + netem？**

A：需要一个人为可控的环境：nginx 提供固定页面，`tc netem` 固定 RTT，`ip route` 固定 initcwnd。真实站点给外部效度，受控平台给内部效度，两者互补。

**Q14：为什么固定 60 ms？**

A：60 ms 让窗口成为瓶颈，慢启动阶段可见；Windows 侧 ping 实测 RTT 稳定在约 65 ms。受控页面 21 个请求、1 235 397 B，足以填满首窗口。

**Q15：initcwnd 为什么写在 on-link 路由上？**

A：WSL2 里响应包走 on-link 网段路由，不是默认路由；只改默认路由不生效。60 KB 单对象实测改前 0.40 s、改后 0.20 s 才说明改对了。WSL 空闲几秒会自动关机，采集期间要保活。

**Q16：平台 MSS 为什么是 1392？**

A：WSL2 网卡 MTU 1432，客户端 SYN 报 1460、服务器 SYN-ACK 报 1392，取较小值 1392；四组折算正好 2/4/10/20，与 `ip route` 设定值一致。

**Q17：为什么用 CDP，不用 Lighthouse？**

A：CDP 能精确等到 `Page.loadEventFired`，并在同一上下文读 Navigation Timing；Lighthouse 基于模拟网络和固定脚本，网络条件不可控。测量流程是启动 Chrome、连 websocket、启用 Page/Network/Runtime，`Page.navigate` 后取导航计时和资源条目。

**Q18：冷缓存和禁 QUIC 怎么保证？**

A：每轮全新 Chrome profile，没有可复用的 HTTP 缓存、DNS 缓存和连接池；进入页面后再显式清缓存。Chrome 统一 `--disable-quic`，每轮检查实际协商协议，出现 h3 即判不合规、拒绝入库。正式数据要求 `quic_disabled=true`、`cache_mode=cold`。

**Q19：122/125 和 IQR 是怎么回事？**

A：真实站点每站 5 轮，sina 缺第 1、4 轮，taobao 缺第 3 轮，均为导航超时，共 122/125 轮，完整率 97.6%。统计时按 `load_ms` 做 IQR 剔除，样本少于 4 轮不剔除；复核后真实保留 108/122 轮，lab 保留 16/20 轮，剔除只用于中位数与箱线图，不改原始 CSV。

**Q20：amazon、yahoo、microsoft 怎么处理？**

A：amazon、yahoo 是防爬拦截页，传输只有 1 633 B / 3 669 B、请求数 2 / 3，加载时间不代表真实首页；保留是为了不选择性删除数据，只在正文标注，它们只会削弱相关。microsoft 的 initcwnd 只有 1/2 轮有效，3.01 MSS 由单轮首飞 4 096 B 折算，代表性弱于其他站点。

**Q21：36kr 的 2 轮 load=0 呢？**

A：按预设 IQR 规则没有剔除（同组还有 304、315、494 ms），主结果保留并在报告中标注。敏感性检查只剔除这 2 轮、保留其余 3 轮，load 中位数 315.0 ms，ρ = −0.304（p = 0.139）；若整站剔除，ρ = −0.214（p = 0.315），均不显著，结论不变。

**Q22：6 个 HTTPS 站 tls_ms=0 怎么解释？**

A：这是已知数据质量问题，与 URL 协议不符；`tls_ms` 不参与本文任何推断，TTFB、load、initcwnd 的结论不受影响。

## 四、C 的统计与结论（A 代表小组回答）

**Q23：真实站点相关性不显著，是不是说明 initcwnd 没用？**

A：不能。只能说在这 25 站、单机单点、每站 3～5 轮的样本上未观察到显著相关。页面字节从 1.6 KB 到 4.37 MB、load 从 304 ms 到 28.5 s，内容方差远大于首窗口的影响；amazon、yahoo 还是拦截页。相关证据只作描述，因果靠受控实验。

**Q24：受控实验校正后 p 都大于 0.05，为什么还敢说“窗口越大越快”？**

A：我们说的是“方向明确、效应量大”，不宣称 5% 水平显著。四组中位数单调下降，效应量 ±1.0（两组完全分离），但 IQR 后每组只有 3～5 个样本，Mann-Whitney U 功效不足。结论按“方向明确、强度待扩样确认”表述。

**Q25：18.2% 和 35.9% 怎么算？**

A：用中位数相减再除以 lab-2：(596.65 − 729.55) / 729.55 = −18.2%；(467.60 − 729.55) / 729.55 = −35.9%。全部由脚本从 CSV 计算，没有手填。

**Q26：为什么 4→10 几乎没有变化，10→20 又降了 21.6%？**

A：受控页面单个对象 61 440 B。2 MSS 首窗只有 2 784 B，2→10 收益最大；10 MSS 首窗 13 920 B 覆盖约 23% 的对象，4→10 出现平台；20 MSS 首窗 27 840 B 覆盖约 45%，仍有收益。曲线形状与对象大小、RTT 组合有关，不外推到所有页面。

**Q27：为什么 IQR 后每组只剩 3～5 个样本？**

A：受控组组内波动极小，IQR 边界很窄，任何略快或略慢的轮次都会被判为异常，例如 lab-4 从 5 轮减到 3 轮。这是预设规则在小样本、低方差分布上的副作用。我们保留主结果，同时在报告 5.1 节给出“保留全部 5 轮”的敏感性检查：中位数 728.4/599.3/595.2/467.6 ms，方向不变。

**Q28：如果改用精确检验，会不会显著？**

A：不会改变结论。精确检验的原始 p 为 0.016～0.057，6 次 Bonferroni 校正后为 0.095～0.343，仍大于 0.05。所以“校正后不显著”不是正态近似造成的假象。

**Q29：为什么用 Spearman 和偏相关，不用 Pearson？**

A：网络延迟通常非正态，样本里有 github 10 440 ms、sina 28 496 ms 这样的长尾；Spearman 基于秩，对异常值和非线性单调关系更稳健。页面总字节是明显混杂因素，所以用偏 Spearman 控制 `transfer_bytes`。

**Q30：Bonferroni 是不是太保守？**

A：6 次两两比较确实保守，但这是预先声明的多重比较校正，避免把偶然的 0.02 当成发现。我们也报告了未校正 p 和精确检验结果，结论一致：方向明确，但校正后不显著。

**Q31：和 RFC 6928 比，结论是什么？**

A：实测中位数 3.78 MSS，明显低于 RFC 6928 建议的 10 MSS，存在提升空间；受控实验给出 2→10 下降 18.2% 的受限证据。建议 10 MSS 起步、20 作为候选，小范围灰度复测。

**Q32：样本要多大才能显著？**

A：本文不做功效计算，也不承诺具体样本量。现有每组 3～5 个样本功效不足；正确做法是扩样后复测，用同一套 IQR、Mann-Whitney U 与 Bonferroni 流程重算。

**Q33：数据可复现吗？**

A：可以。`python -m src.analysis` 从 `data/processed/initcwnd.csv` 与 `pageload.csv` 重出图 3～6 与表 2～4；剔除规则、字段校验、图注都在仓库内。分析复核记录见 `docs/实验记录.md` 的 EXP-20261104-02。

**Q34：如果老师追问“因果效应到底多大”，怎么答？**

A：在受控条件下，2→10 使 load 中位数从 729.55 降到 596.65 ms（−18.2%），2→20 降到 467.60 ms（−35.9%）；这是固定 60 ms RTT、固定 1 235 397 B 页面的结果，不能当作公网预期收益。
