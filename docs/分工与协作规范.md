# 分工与协作规范

本文件是三人日常协作的操作手册。技术方案见 `docs/项目总体设计.md`。

---

## 一、角色与代码归属

- **A**：`src/capture/`、`tests/test_capture_*.py`、Git 与 CI、仓库维护
- **B**：`src/measure/`、`experiment/server/`、`tests/test_measure_*.py`、`config/sites.csv`
- **C**：`src/analysis/`、`tests/test_analysis_*.py`、`docs/数据字典.md`、报告统稿
- **公共**：`src/common/`、`config/settings.yaml`、`README.md`、`docs/项目总体设计.md` 由三人共同维护，改动必须走 PR 并经另外两人确认

**不要越界改别人的目录。** 发现别人代码有问题，提 issue 或在 PR 里评论，让本人改。

---

## 二、分支模型

采用 GitHub Flow：

- `main`：始终可运行，开启分支保护，禁止直接 push，只接受 PR
- `feature/capture`：A 的长期分支
- `feature/measure`：B 的长期分支
- `feature/analysis`：C 的长期分支

子任务可以在自己的 feature 分支里再切短分支，但最终合并回自己的 feature 分支，再向 `main` 提 PR。

**合并方式统一用 Merge commit，不用 Squash。** 目的是保留真实的分支线，答辩时 `git log --graph --all --oneline` 能展示三条并行开发线的版本树。

---

## 三、提交规范

格式：`type(scope): 描述`

- type：`feat`（新功能）、`fix`（修 bug）、`docs`（文档）、`test`（测试）、`refactor`（重构）、`chore`（杂项）
- scope：`capture`、`measure`、`analysis`、`common`、`docs`、`config`、`ci`

示例：

```
feat(capture): 实现三次握手识别
fix(capture): 修正重传去重时序号区间合并错误
docs: 补充数据字典中 confidence 的判定标准
test(analysis): 增加偏相关函数测试
```

要求：

- 一次提交只做一件事，不把无关改动混在一起
- 描述用中文，写清"做了什么"，不写"更新文件"这种空话
- 每天至少 push 一次自己的分支，禁止长期本地堆积

---

## 四、PR 与评审

**流程**：

1. 在自己的 feature 分支完成一个可验证的小功能，`pytest` 全绿
2. push 到 GitHub，发起 PR 到 `main`
3. 填写 PR 模板（改动内容、影响范围、自检项）
4. 指定评审人，评审人 24 小时内给出意见
5. 评审通过后由 PR 发起人自己执行 Merge commit
6. 合并后删除临时分支，保留三条长期 feature 分支

**评审轮转**：A 审 B、B 审 C、C 审 A。评审人至少检查三件事：改动是否越界、测试是否覆盖新逻辑、数据字段是否被私改。

**公共契约变更**（`src/common/schema.py`、`config/settings.yaml`）必须三人全部确认才能合并。

## 五、版本标签

- `v0.1.0`：骨架完成（2026-10-30）
- `v0.5.0`：两套数据采集完成（2026-11-04）
- `v1.0.0`：答辩冻结版（2026-11-07）

打标签命令：

```bash
git tag -a v0.1.0 -m "骨架：目录、公共模块、数据契约、CI"
git push origin v0.1.0
```

## 六、首次推送 GitHub

仓库由组长或 A 创建后，每人执行：

```bash
git remote add origin <仓库地址>
git push -u origin main
git checkout -b feature/capture     # 各自换成自己的分支名
git push -u origin feature/capture
```

**注意**：仓库地址、组员 GitHub 账号、邀请协作者由组长统一办理；推送前确认 `.gitignore` 生效，`data/raw/` 下的 pcap 不得进入提交。

---

## 七、日常协作流程

每天固定三件事：

1. 早上 `git pull origin main`，把自己的 feature 分支 rebase 到最新 main
2. 晚上 push 自己的分支，并在群里同步"今天做了什么、卡在哪、明天做什么"
3. 有任何实验数据产出，当天登记到 `docs/实验记录.md`

冲突处理：在自己分支上解决冲突，解决完必须跑一遍 `pytest` 再 push；禁止用 `git push -f` 覆盖别人的提交。

---

## 八、禁止事项

- 禁止直接向 `main` push
- 禁止提交 `data/raw/` 下的 pcap、`.venv/`、`.idea/`
- 禁止在 feature 分支私改 `src/common/schema.py` 的字段
- 禁止用 `git push -f`、`git reset --hard` 处理别人的分支
- 禁止把未通过 schema 校验的数据写进 `data/processed/`
- 禁止在真实实验中关闭 QUIC 检查或跳过冷缓存
- 禁止对非公开站点、非首页路径做扫描或压测

---

## 九、测试与 CI

- 本地：提交前必须 `pytest` 全绿
- CI：每次 push 和 PR 自动运行 `.github/workflows/tests.yml`
- 新功能必须带测试，公共模块的测试覆盖率优先保证
