## 讲稿

**0:00–0:30 开场**

我负责报告中的数据测量与实验平台。这部分要回答两个问题：数据是怎么测出来的，以及凭什么相信它可信。报告用两条线：25 个真实站点提供外部效度，受控平台提供内部效度。

**0:30–2:00 受控实验平台**

（切到图 2）平台架在本机 WSL2 里，Ubuntu 24.04、内核 6.6.114，由四部分组成。服务端是 nginx，根目录放 1 个索引页和 20 个精确 61440 字节的合法 PNG，整页 21 个请求、1 235 397 字节。时延用 `tc netem` 在出口网卡加 60 毫秒，Windows 侧 ping 实测稳定在 65 毫秒。窗口控制用 `ip route` 给出口路由设 `initcwnd`，取 2、4、10、20 四档。测量端是 Windows 上的 Chrome，采集逻辑和真实站点完全一样。

有两个坑值得说。第一，initcwnd 必须写在回程真正走的那条路由上。WSL2 里响应走 on-link 网段路由，只改默认路由不生效，单个 60 KB 对象实测从 0.40 秒降到 0.20 秒才说明改对了。第二，WSL 虚拟机会在空闲数秒后自动关机，采集期间必须挂一个常驻会话，否则请求直接被拒。

还有一个口径问题：MSS 取客户端 SYN 和服务器 SYN-ACK 的较小值。平台 MTU 是 1432，两端取小是 1392，所以四组折算下来正好是 2.0、4.0、10.0、20.0；如果沿用 1460，10 MSS 会被算成 9.53。

**2:00–3:00 指标定义与测量方案**

（切到表 1）测量用 Chrome DevTools 协议驱动浏览器，不用页面埋点，因为它能精确等到 load 事件，并在同一上下文里读 Navigation Timing。流程是：启动 Chrome 暴露调试端口，连 websocket，启用 Page、Network、Runtime 三个域；`Page.navigate` 之后等 `Page.loadEventFired`，再用 `Runtime.evaluate` 取导航计时和全部资源条目。

六个指标全部以导航开始为原点：DNS、TCP、TLS、TTFB、DOMContentLoaded、load。换算公式就是第 2 章给的那几条，比如 TTFB 是 `responseStart` 减 `requestStart`。TTFB 反映首窗口能不能在一个 RTT 内出数据，load 反映整页受不受首窗口影响。

**3:00–4:30 数据采集与质量控制**

真实站点先做可达性预检：36 个候选测一轮，8 个不可达，从 28 个可达站点里选 25 个，国内 18、国际 7。每站连续 5 轮，同一时段、同一台机器、同一网络，任意时刻只跑一个测量进程。

质量上有三条硬约束。冷缓存：每轮全新临时用户目录，没有可复用的 HTTP 缓存、DNS 缓存和连接池，进页面后再显式清缓存。禁 QUIC：Chrome 统一加 `--disable-quic`，每轮还检查实际协商协议，出现 h3 就判为不合规、拒绝入库。统计：每站按 load 时间用 IQR 剔除异常轮，样本少于 4 轮不剔除，最后取中位数。

本批次 122 / 125 轮，完整率 97.6%，25 个站点都保留至少 3 轮。受控平台另做有效性校核，四组各 5 轮，load 中位数依次是 728.4、599.3、595.2、467.6 毫秒，单调下降，TTFB 稳定在 65.8 到 66.1 毫秒，传输字节恒为 1 235 397。

**4:30–5:00 结论与交接**

两条线的数据都通过字段校验后写入 `pageload.csv`，再和抓包得到的 initcwnd 按站点合并。内容不变、时延不变，只改窗口，加载时间就变了，这说明因果关系成立。后面由 C 做统计分析，A 讲抓包算法。

## 预设问答

**Q1：为什么不用 Lighthouse 或 WebPageTest？**
它们的指标基于模拟网络和固定脚本，网络环境不可控；本文要控制的是 initcwnd 这个内核参数，必须自己搭平台、自己读数。

**Q2：禁 QUIC 对结果有什么影响？**
HTTP/3 走 QUIC，没有 TCP 慢启动和线性增长，initcwnd 对它无意义。禁掉之后所有站点统一走 TCP，口径一致。

**Q3：IQR 剔除会不会把真实差异删掉？**
规则只看同一站点内部的轮次分布，不跨站点比较；且样本少于 4 轮不剔除，避免小样本误删。剔除数量和位置都写进了实验记录。

**Q4：DNS 缓存怎么保证是冷的？**
每轮新 profile 意味着空 DNS 缓存，但操作系统层仍可能缓存。命中缓存时 `dns_ms` 会接近 0，notes 里会注明，分析时不影响 TCP 与 TTFB 的结论。

**Q5：5 轮够不够？**
课程项目的样本量，重点在可比性而非统计功效。5 轮取中位数加 IQR 已能压住单轮抖动，受控组组内波动小于 1% 就是证据。

**Q6：为什么真实站点只测首页？**
首页是用户接触最多的入口，且请求数与资源构成相对稳定；深层页面的资源结构差异太大，不适合做跨站点比较。

### 现场演示脚本（已预演）

预演环境：Ubuntu 24.04 on WSL2，内核 6.6，nginx 监听 8080，页面为 1 个索引页 + 20 个 61440 byte 对象。

| 步骤 | 命令 | 预演耗时 |
|---|---|---|
| 1 保活虚拟机 | `wsl -d lab-ubuntu -u root -e sleep infinity` | 即时 |
| 2 确认服务 | 浏览器或 `curl http://<wsl-ip>:8080/` 应返回 200 | VM 冷启动到可用 < 10 秒 |
| 3 取当次 IP | `wsl -d lab-ubuntu -u root hostname -I` | 重启后 IP 会变，必须现取 |
| 4 加时延 | `set_netem.sh 60`，`ping` 应见 RTT ≈ 65 ms | 1 秒 |
| 5 低窗口组 | `set_initcwnd.sh 2` 后采 2 轮 | 6 秒，实测 688 / 678 ms |
| 6 高窗口组 | `set_initcwnd.sh 20` 后采 2 轮 | 6 秒，实测 439 / 436 ms |
| 7 收尾 | `set_netem.sh clear`、`set_initcwnd.sh 10` | 1 秒 |

两组中位数 683 ms vs 438 ms，比值 1.56，与正式数据（728 / 468 ms）一致，现场可直接口述这个结论。

注意事项：

- 虚拟机空闲约 8 秒会自动关机，演示前必须先执行第 1 步，否则第 2 步会连接被拒
- `initcwnd` 与 `netem` 都不持久化，每次演示都要重设；收尾必须清除 netem，否则下次真实站点测量会被污染
- 命令回显不能作为"初窗已生效"的证据，答辩时说明这一点，可体现方法严谨性
- 兜底方案：准备 CSV 截图与图 2，避免现场环境异常时冷场
