## 1. 项目概述

本项目回答一个真实的网络工程问题：**服务器的初始拥塞窗口（initcwnd）对网页加载性能到底有多大影响，服务器该不该调它。**

项目不是复现课本实验，而是走完一条完整的网络测量链路：协议原理分析 → 抓包测量 → 浏览器性能测量 → 受控实验 → 统计推断 → 可视化与报告。三个成员各自负责一条端到端的工作线，最后合并成一份可复现、可验证、有因果结论的成果。

## 2. 研究问题与结论分级

**Q1（事实）**：真实网站服务器的 initcwnd 实际分布如何？

**Q2（相关）**：initcwnd 与页面加载性能指标是否相关、相关多强？

**Q3（因果）**：在控制网络条件、页面内容等变量的前提下，改变 initcwnd 对加载时间有多大影响？

结论必须分级表述，不允许混用：

- 真实站点数据只能支撑 **"相关"** 结论，报告里写"观察到……与……存在相关性"；
- 受控实验数据才能支撑 **"因果"** 结论，报告里写"在控制变量的条件下，initcwnd 从 2 增大到 10 使加载时间下降……"。

这条纪律是"分析严密"评分的核心，也是答辩时最容易被追问的地方。

## 3. 实验原理

**慢启动与初始拥塞窗口**：TCP 连接建立后，发送方不能一次性把数据全发出去，而是以初始拥塞窗口为上限开始发送，每收到确认就扩大窗口。initcwnd 就是这个"起跑线"。

**initcwnd 的定义**：服务器在收到客户端第一个 ACK 之前，允许发送的未确认数据量。Linux 自 3.0 起默认约为 10 个 MSS，RFC 6928 建议值也是 10 个 MSS；但不同操作系统、不同 CDN、不同服务器配置的实际值差异很大，这正是我们要测的。

**测量方法**：客户端抓包（scapy），识别 TCP 三次握手，统计服务器在收到第一个 ACK 之前发出的**载荷字节数**，再除以 MSS 得到 initcwnd 的 MSS 倍数。

**MSS 的取法**：从 SYN 报文的 MSS 选项字段读取，不写死 1460，避免 IPv6 和隧道场景出错。

**误差来源**：重传、乱序、网卡 GRO/LRO 合并、TSO 分段。对策是**只统计字节数、不统计段数**，重传按序号区间去重，并在受控实验里用已知真值验证算法。

**页面加载指标**：DNS 解析、TCP 连接、TLS 握手、TTFB、DOMContentLoaded、load、资源请求数、传输字节数。

## 4. 总体技术路线

### 4.1 三层事实 + 一个闭环

**第一层（事实）**：真实网站服务器的 initcwnd —— 被动抓包，A 负责。
**第二层（事实）**：真实网站的页面加载性能 —— 浏览器测量，B 负责。
**第三层（因果）**：人为改变 initcwnd 后的加载时间变化 —— 受控实验，B 搭平台、A 校准、C 分析。

**闭环（自校准）**：受控实验中的 initcwnd 是人为设定的已知真值（2/4/10/20）。先用这些真值验证 A 的测量算法，误差必须不超过 1 个 MSS；算法被证明可信之后，才允许拿去测真实网站。这一步是全项目可信度的基石。

**双证据链**：真实站点数据给出相关性，受控实验给出因果性，两种证据在报告里互相印证。

### 4.2 两条铁律

**铁律一：测 initcwnd 必须用 curl 单连接。** 浏览器会并行开 6 条以上连接，首窗口互相干扰，测出来的是噪声。

**铁律二：测加载性能必须禁用 QUIC。** 大量站点默认走 HTTP/3（QUIC），而 QUIC 有自己的初始窗口机制，与 TCP initcwnd 不是一回事。Chrome 启动时加 `--disable-quic`，保证两组数据可比。

### 4.3 受控实验设计

- 环境：WSL2 内运行 nginx，Windows 侧浏览器访问
- 网络条件：`tc qdisc ... netem delay` 构造固定 RTT（默认 60 ms），让窗口大小真正成为瓶颈
- 变量：`ip route change ... initcwnd N`，取 N = 2、4、10、20 四组
- 页面：生成 20 个 60 KB 对象的测试页，总量约 1.2 MB，足以让慢启动阶段可见
- 每组重复 5 轮，取中位数
- 每组同时抓包，验证设定值与实测值一致

## 5. 数据契约

两份 CSV 是三人之间**唯一的数据接口**。字段定义在 `src/common/schema.py`，说明在 `docs/数据字典.md`。任何字段增删改都必须走 PR 并三人确认。

### 5.1 `data/processed/initcwnd.csv`（A 产出）

- `site`：站点标识，必须与 `pageload.csv` 一致；受控实验统一写 `lab-<initcwnd值>`
- `url`：被测 URL
- `server_ip`：服务器 IP
- `ip_version`：`4` 或 `6`
- `timestamp_utc`：采集时间，ISO 8601，UTC
- `initcwnd_bytes`：首窗口字节数
- `mss_bytes`：MSS 字节数
- `initcwnd_mss`：initcwnd 的 MSS 倍数
- `segment_count`：首窗口内报文段数量（仅供参考，不作为结论依据）
- `retrans_count`：首窗口内重传数量
- `method`：`passive`（真实站点）或 `lab`（受控实验）
- `confidence`：`high` / `medium` / `low`
- `notes`：备注

### 5.2 `data/processed/pageload.csv`（B 产出）

- `site`、`url`：同上
- `run_id`：组内序号
- `timestamp_utc`：采集时间
- `dns_ms`、`tcp_ms`、`tls_ms`、`ttfb_ms`、`dom_content_loaded_ms`、`load_ms`：各阶段耗时（毫秒）
- `request_count`：资源请求数
- `transfer_bytes`：页面总传输字节
- `quic_disabled`：`true` / `false`，真实实验必须为 `true`
- `cache_mode`：`cold` / `warm`，正式数据必须为 `cold`
- `network_env`：网络环境描述（有线/无线、运营商、时段）
- `notes`：备注

### 5.3 合并规则

- 合并键：`site`
- 受控实验通过 `site` 前缀 `lab-` 识别；`lab-2`、`lab-4`、`lab-10`、`lab-20` 对应四组
- 合并前两边都要通过 schema 校验；校验不通过的数据不得进入分析

## 11. 评分表映射

### 11.1 课程培养目标、难度与工作量、创新性与实用性

课程培养的是"协议原理 + 网络测量 + 工程实践"。项目沿 TCP 慢启动、拥塞窗口、MSS 展开协议分析，用 scapy 抓包与浏览器测量完成数据采集，用 Git 分支、PR、CI 完成工程协作，三项能力一条线打通。

难度不在代码量，在三个必须自己趟过去的坑：协议层的序号跟踪与网卡合并、系统层的 WSL 网络与内核参数、数据层的非参数统计方法选择。工作量三人各约 6 人天，合计约 1450 行代码、25 个站点、两套数据集、六章报告。

实用性在于输出一份可直接指导服务器调优的量化结论：initcwnd 调到多少对首屏有意义、值不值得调。

### 11.2 任务要求、设计科学性先进性、计算准确性、图表国标

任务拆成六项可验收交付物：可运行代码、两份带数据字典的 CSV、四张规范图表、六章报告、答辩演示、完整版本仓库。

设计上坚持控制变量：单连接测窗口、禁 QUIC、冷缓存、固定重复次数、记录网络环境。先进性体现在用 Chrome DevTools 协议而非 Selenium，用 scapy 数据包级解析，用 WSL2 + tc netem 构造可调网络，用 Spearman 与偏相关而非目测散点。

计算准确性有三道保险：initcwnd 按字节数除以 MSS 计算，MSS 从 SYN 选项读取；算法用受控真值校准，误差不超过 1 个 MSS；统计结论必须给出检验方法、p 值与效应量。

图表按国家标准执行：图题在下、表题在上、全文连续编号、三线表、量符号斜体单位正体、流程图符号符合 GB/T 1526、参考文献按 GB/T 7714-2015、报告结构按 GB/T 7713.1。

### 11.3 创新性与实用价值

创新点一，**自校准测量法**：用已知真值的受控服务器反验证抓包算法，再测真实网站，避免"算法说多少就是多少"。

创新点二，**双证据链**：真实站点给相关性，受控实验给因果性，两类证据互相印证。

创新点三，**真实站点普查加受控对照**：25 个真实站点给出实际分布，四组受控实验给出干净的因果曲线。

实用价值：给出可操作的 initcwnd 调优参考；工具链可复现、可迁移；"自校准 + 双证据"的方法可复用到其他网络参数测量。

### 11.4 分析、计算、实验的正确性与严密性

控制变量写死在配置文件里：同机、同时段、同网络、冷缓存、禁 QUIC、固定重复次数；抓包实验与加载实验分开执行，避免相互干扰。

算法正确性用受控真值证明；时间指标取中位数避免超时包拉偏；异常值按四分位距规则剔除，剔除规则和数量写进报告。

统计方法匹配数据性质：网络延迟通常非正态，用 Spearman 秩相关；页面总大小是混杂因素，用偏相关控制；分组比较用 Mann-Whitney U 检验并报告效应量。

结论严格分级：真实数据只说相关，受控数据才说因果。

## 13. 风险与对策

**WinPcap 兼容性**：本机为 eNSP 保留 WinPcap 4.1.3，未安装 Npcap。先用 `check_env.py` 验证 scapy 能否正常抓包；失败则改用 WSL2 内 tcpdump 采集。

**WSL 网络与权限**：WSL2 默认 NAT，Windows 侧访问需用 WSL IP 或端口转发；`tc` 与 `ip route` 需要 root。平台脚本统一写成可重复执行的 shell，并在实验记录里注明 WSL 版本。

**QUIC 干扰**：浏览器默认走 HTTP/3，必须 `--disable-quic`，数据中 `quic_disabled` 必须为 `true`。

**GRO/LRO 合并**：网卡会把多个段合并成一个大段，导致段数失真；算法只统计字节数。

**时间紧**：11/03 是质量关卡，校准不通过就砍掉受控实验，保留真实站点数据与相关分析，保证有可交付结论。

**站点不可达**：站点清单预留 22 个候选，实际采集 25 站时可补充；不可达站点记录原因并从统计中剔除。

**GitHub 访问不稳定**：先保证本地仓库完整，推送失败不阻塞开发；答辩前完成推送并在 README 附仓库地址。

**数据不一致**：11/04 数据冻结；冻结后只允许修订明显错误并记录在实验记录中。

## 14. 术语表

- **initcwnd**：初始拥塞窗口，TCP 连接建立后发送方首个窗口的大小
- **MSS**：最大报文段长度，TCP 单个报文段能携带的最大载荷字节数
- **cwnd**：拥塞窗口，发送方维护的"未被确认数据量"上限
- **RTT**：往返时延
- **慢启动**：连接初期窗口快速增长的阶段
- **TTFB**：首字节时间，从请求发出到收到第一个响应字节
- **DCL**：DOMContentLoaded，DOM 解析完成的时间点
- **CDP**：Chrome DevTools Protocol，Chrome 调试协议
- **GRO/LRO/TSO**：网卡的分段/合并卸载技术，会影响抓包看到的报文形态
- **QUIC**：基于 UDP 的传输协议，HTTP/3 的底层，有自己的初始窗口
- **netem**：Linux 流量控制中的网络模拟模块，可加延迟、丢包、抖动
- **pcap**：抓包文件格式
