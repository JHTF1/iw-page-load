# 第 2 章 相关原理

本章给出后续测量与分析所依赖的两组原理：TCP 慢启动阶段的拥塞窗口与初始拥塞窗口（initcwnd），以及页面加载各阶段的时间指标。明确这两组概念之后，第 3 章的抓包算法与第 4 章的浏览器测量方案才有统一的解释框架。

## 2.1 TCP 慢启动与拥塞窗口

TCP 用拥塞窗口（congestion window，`cwnd`）限制发送方在未收到确认前可以注入网络的数据量，它是发送速率的直接控制量。连接建立时发送方并不知道链路容量，因此从慢启动（slow start）开始：每收到一个确认，`cwnd` 增加一个 MSS，等价于每经过一个往返时间（RTT）窗口翻倍，呈指数增长，直到触及慢启动阈值或发生丢包[1]。

慢启动阶段的有效吞吐由首窗口决定。设初始拥塞窗口为 `initcwnd` 个 MSS，则发送方在收到第一个 ACK 之前最多可以发出

```
W0 = initcwnd × MSS
```

字节。当被请求的对象小于 `W0` 时，整个对象可以在一个 RTT 内交付完毕，连接的有效完成时间近似为一次往返；当对象大于 `W0` 时，剩余字节必须等待后续窗口扩张，完成时间随对象大小呈阶梯式增长。这个边界使 initcwnd 对短连接、小对象的性能影响远大于对长流量传输的影响。

## 2.2 initcwnd 与 RFC 6928

RFC 5681 最初将 `initcwnd` 限制为不超过 4 个 MSS（约 4~6 KB）。RFC 6928 于 2013 年将其上限提高到 10 个 MSS，主要依据是当时 Web 响应体的中位大小已超过首窗口容量：窗口过小会让大量本可一次往返传完的响应被迫多等一个 RTT，而 10 个 MSS 带来的突发量在现代链路缓冲下不足以引发拥塞崩溃[2]。

MSS 由链路 MTU 决定而非固定值：以太网 MTU 为 1500 字节时，IPv4 的 MSS 通常为 1460 字节，IPv6 为 1440 字节。因此 10 个 MSS 对应约 14.6 KB（IPv4）。实际部署中 initcwnd 仍是可配置的内核参数，不同操作系统、CDN 与服务器软件的默认值并不一致，这构成了本文要测量的经验事实（Q1）。

## 2.3 页面加载时间指标

现代浏览器通过 Navigation Timing 记录页面加载各阶段的时间戳，本文采用六个指标，全部以毫秒为单位、以导航开始为共同原点：

- **DNS 解析（`dns_ms`）**：域名查询耗时，对应 `domainLookupEnd - domainLookupStart`；
- **TCP 连接（`tcp_ms`）**：三次握手耗时，对应 `connectEnd - connectStart`；
- **TLS 握手（`tls_ms`）**：仅 HTTPS 站点存在，对应 `connectEnd - secureConnectionStart`，纯 HTTP 站点记为 0；
- **首字节时间（`ttfb_ms`）**：请求发出到收到首个响应字节，对应 `responseStart - requestStart`，它直接受首窗口与 RTT 影响；
- **DOMContentLoaded（`dom_content_loaded_ms`）**：HTML 解析完成、延迟脚本执行完毕的时刻；
- **load（`load_ms`）**：页面及其资源全部加载完成的时刻。

其中 `ttfb_ms` 与 `load_ms` 是本文最关心的两个量：前者反映首窗口能否在一个往返内交付响应头与初始数据，后者反映整页在多大程度上受初始突发能力影响。由于 `load_ms` 同时受页面总字节数与请求并发度影响，分析时必须把 `transfer_bytes` 与 `request_count` 作为控制变量，否则无法把 initcwnd 的作用与"页面大小"这一混杂因素分开（第 5 章）。

## 2.4 本章小结

initcwnd 通过首窗口字节数决定短连接能否在一个 RTT 内完成交付，RFC 6928 将其上限提高到 10 个 MSS；页面加载的六个时间指标为此提供了可观测的落点。后续测量需要同时给出"服务器实际使用的 initcwnd"（第 3 章抓包）与"客户端观测到的加载时间"（第 4 章浏览器测量）两类证据。
